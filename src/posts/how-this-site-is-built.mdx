These days whenever I start a new project the first thing I ask myself is how I'm going to host it; because that determines the tech stack and the whole approach. Given that you can basically do anything however you want in web development, I always have an overwhelming amount of options.

There was a time when I wanted to self host everything, and I got a lot of joy out of playing sysadmin and managing my very own pet servers, making sure they were secure and healthy. These days the less time I have to spend managing or thinking about a sever the better - I've got other things I'd rather be doing! I don't mind paying, but there are a lot of options for free hosting, so that has to be an aim.

<Callout variant="info" title="Are servers pets or cattle?">
  A pet server is lovingly unique, often named, and usually has all its config
  set manually. It gets fixed when something breaks. Whereas cattle are
  automated and disposable. If one breaks, it is replaced.
</Callout>

When considering where to host, these are the questions I ask about the project:

- Do I need a database? What's the state, where does it live and when does it change?
- Is the site dynamic or static? How interactive is it? Should pages be rendered on the server, the client, or some combination of both?
- Who's managing the content, do we need a CMS?
- Do we need a contact form or any other forms?
- Are there any scheduled jobs, events or real-time connections needed?
- How much traffic am I expecting and how annoying would it be to move hosting?

I have some usual suspects depending on the answers to those questions.

By describing this site, I could answer those questions:

- The content is markdown blog posts that live in the github repo.
- The site is static, it only changes on re-deploy.
- It's only me adding content and I don't need a CMS.
- It could get away without a contact form, but it would be nice to have one.
- No scheduled jobs, events or real-time connections needed.
- Not much traffic expected and trivial to move static pages.

The answer: Netlify.

Why? Netlify is free and it's easy. By free I mean very generous limits that this little site would never come close to hitting. It can also be setup to deploy via git push, upon which it will run a build command and serve the static output, making redeploying a breeze.

They also provide a CDN, deploy previews (essentially a staging domain), automated SSL cert provisioning and renewal. Those are all things I could easily setup myself, but why bother when Netlify does them out of the box.

This isn't even an ad, I promise. There are competitors and alternatives of course - Cloudflare, Github Pages, Vercel, Render and more. Take your pick really. But I have had a good experience with Netlify. Netlify if you do want to pay me to advertise for you, please reach out and I'll say more nice things!

Once I knew I wanted a static site with a blog, I had to reach for a generator. The original version of this site was a flat, hand-written static site with a single HTML file, a single CSS and JS file and no build tooling:

```
v1/
  ├── index.html
  ├── scripts.js
  ├── styles.css
  ├── img/
```

Given that this new version of the site is going to have a blog, it needs better templating. Even if didn't, I'd like a more modern developer expeience.

I've used Eleventy extensively recently but I don't want to use it this time for a couple of reasons. Firstly, it's so barebones that I always find myself rebuilding my own versions of features that ship by default in something like Astro. Secondly, since there are no conventions with eleventy I find myself deciding where everything will go and how it will work, and decison fatigue is real, I also get sick of reinventing the wheel.

So I could have gone and copied the strucuture and setup from a previous eleventy project, but I decided it was a good time to try something different.
